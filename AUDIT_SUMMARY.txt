CRITICAL REMAINING BUGS
=======================

❌ BUG 1: Razorpay Order Duplication on Concurrent Requests
   --------
   Severity: HIGH
   
   What: Two simultaneous POST /api/payments/create requests create TWO Razorpay orders
         instead of ONE
   
   Why: INSERT ... ON CONFLICT prevents duplicate Payment records, but BOTH requests
        then proceed to call razorpayClient.createOrder() independently
   
   Scenario:
     Request A: INSERT Payment → createRazorpay Order X → PaymentAttempt #1 (order_ABC)
     Request B: (concurrent) INSERT with conflict → DO UPDATE → createRazorpay Order Y → PaymentAttempt #1 (order_XYZ)
   
   Result:
     - 1 Payment record ✅ CORRECT
     - 2 PaymentAttempt records with attempt_number=1 ❌ WRONG  
     - 2 different Razorpay orders created ❌ WRONG (waste of API calls)
     - Frontend gets inconsistent razorpay_order_id ❌ WRONG
   
   Code Issue: Lines 181-187 in PaymentService.ts
     Both requests reach createRazorpayOrder() because the status check on line 172
     doesn't differentiate between first-time and concurrent calls properly.


❌ BUG 2: Payment Retry After User Cancels Razorpay
   --------
   Severity: HIGH
   
   What: User cancels Razorpay modal → clicks "Retry Payment" → Gets 409 Conflict
   
   Why: When user cancels Razorpay without paying, Payment status stays 'pending'
        Backend retry logic only allows new attempt if status='failed'
        Cancellation never marks Payment as 'failed'
   
   Code: Lines 172-180 in PaymentService.ts
     if (paymentData.status === 'failed') {
       // Only this case creates new attempt
     }
     // 'pending' status blocks retry

   Result: User cannot retry after cancellation without manual DB intervention


❌ BUG 3: Duplicate PaymentAttempt attempt_number Generation
   --------
   Severity: MEDIUM
   
   What: Concurrent requests can both create PaymentAttempt with same attempt_number
   
   Why: MAX(attempt_number) + 1 pattern is not atomic across transactions
   
   Code: Lines 167-169 in PaymentService.ts
     const lastAttempt = await queryRunner.manager.findOne(PaymentAttempt, {...});
     attemptNumber = (lastAttempt?.attempt_number || 0) + 1;
   
   Both transactions can see same lastAttempt.attempt_number, calculate same attemptNumber
   
   Result: Database integrity violation; duplicate attempt numbers

ORDER DUPLICATION CHECK
=======================

Can the same cart produce multiple orders?

Answer: NO - SAFE ✅

Frontend: orderCreationAttempted flag blocks double-submission
Backend: Pessimistic write lock on cart + converted_to_order_id check

Even with concurrent POST /api/orders:
  First call: Locks cart, creates order, sets converted_to_order_id
  Second call: Waits for lock, then finds converted_to_order_id already set
  Second call: Throws "Cart has already been converted to an order" (409)


FRONTEND DUPLICATE REQUEST ROOT CAUSE
======================================

Original Issue: Two POST /api/payments/create in rapid succession (11ms apart)
  09:16:08.891
  09:16:08.902

Root Cause: React.StrictMode effect double-invoke
  In development, React runs useEffect twice to detect impure effects
  Original code had no guard:
    useEffect(() => { initPayment(); }, [orderId])
    // Runs twice, both call POST /api/payments/create

Current Fix: initializationAttempted flag
  First run: flag=false → sets true → calls initPayment()
  Second run: flag=true → returns early (no API call)
  
  Result: Only 1 POST /api/payments/create per mount ✅


PAYMENT ATTEMPT NUMBER CONCURRENCY
===================================

Current Generation (Lines 167-169):
  const lastAttempt = await queryRunner.manager.findOne(PaymentAttempt, {...});
  attemptNumber = (lastAttempt?.attempt_number || 0) + 1;

Is it concurrency-safe? NO ❌

Why:
  Both concurrent transactions can see same lastAttempt.attempt_number
  Both calculate attemptNumber = 1 + 1 = 2
  Both insert PaymentAttempt with attempt_number=2
  Result: Duplicate attempt numbers in database
